Connects a VR headset to the robot (or simulator) for teleoperation. IK runs in a dedicated subprocess to keep JAX off the asyncio event loop. The pipeline is: VR frames → lag-compensated low-pass filtering → IK solve → EMA smoothing → trapezoidal velocity profiling → `motion_control()`.

```python
from almond_axol.teleop import VRTeleop, VRTeleopConfig
```

```python
import asyncio
from almond_axol.robot import Axol
from almond_axol.teleop import VRTeleop

async def main():
    async with VRTeleop(Axol()) as teleop:
        await teleop.run()  # blocking; Ctrl+C to exit

asyncio.run(main())
```

```python
VRTeleop(
    robot: RobotBase,
    *,
    config: VRTeleopConfig | None = None,             # None → teleop.* shared settings
    kinematics_config: KinematicsConfig | None = None, # None → kinematics.* shared settings
    vr_server_config: VRServerConfig | None = None,    # None → vr_server.* shared settings
    jelly: Jelly | None = None,
)
```

Each config left `None` is built from the robot's shared settings file (`~/.almond/settings.json` — the one the [control panel](/guides/control-panel-settings) edits and `axol teleop` reads) over the built-in defaults, so an SDK session runs the same rest poses, multipliers, IK weights and VR port as the panel. Pass a config explicitly to override it; see [Shared settings](/api/robot#shared-settings).

Use `step()` instead of `run()` to integrate teleoperation into your own control loop:

```python
async with VRTeleop(axol) as teleop:
    while True:
        left_q, right_q = teleop.step()  # returns latest smoothed (8,) arrays
        # ... custom logic ...
        await asyncio.sleep(1 / 120)
```

To show camera feeds in the headset, register frame sources after the session is enabled — `VRTeleop.set_video_sources()` forwards them to the VR server's WebRTC relay (requires the GStreamer NVENC stack, installed by [`axol gst.install`](/cli/gst-install); see [`almond_axol.vr`](/api/vr#camera-video-to-the-headset)). Each value is a connected `ZedCamera` (registered directly) or any object exposing `width` / `height` / `fps` + `wait_next`:

```python
async with VRTeleop(axol) as teleop:
    teleop.set_video_sources({"overhead": cam})
    await teleop.run()
```

See the [`teleop`](/cli/teleop) CLI command for the equivalent command-line entry point (`--cameras` wires the ZED cameras up automatically).

<Note>
  `set_video_sources()` runs the WebRTC relay in-process. The CLI instead prefers `VRTeleop.set_video_manager()`, which hands the camera grab/encode and WebRTC off to a dedicated subprocess (`almond_axol.video.video_proc.VideoRelayProcess`) so it can't perturb the control loops. Both deliver the same headset video — see [`almond_axol.vr`](/api/vr#camera-video-to-the-headset).
</Note>

## `VRTeleopConfig` fields

| Field | Default | Description |
|---|---|---|
| `frequency` | `240` Hz | Control loop rate used by `run()` and reset trajectory density |
| `ik_frequency` | `120` Hz | VR-frame ingest / IK dispatch cadence (decoupled from the faster control loop) |
| `teleop_max_vel` | `1.0 rev/s` | Trapezoidal filter velocity cap during normal teleoperation |
| `teleop_max_accel` | `3.5 rev/s²` | Trapezoidal filter acceleration cap |
| `engage_max_vel` | `0.1 rev/s` | Starting velocity cap when teleop is first engaged after a reset; smoothsteps up to `teleop_max_vel` over `engage_duration` |
| `engage_duration` | `1.0` s | Seconds over which the velocity cap ramps (smoothstep) from `engage_max_vel` up to `teleop_max_vel` after engaging |
| `ik_alpha` | `0.3` | EMA blend factor on IK output; `1.0` disables smoothing |
| `pose_cutoff` | `2.5` Hz | Pole of the lag-compensated low-pass on raw VR poses (tremor rejection before IK) |
| `record` | `None` | File prefix for the teleop flight recorder; captures every pipeline stage to `<prefix>_{ik,cmd,meas,rt}.npz` for `axol diag.teleop-jitter`. The compact `rt` stage contains the Rust core's actual 240 Hz motor command, derivative/feedforward/damping terms, timing, and feedback. All stages retain the latest engage→disengage segment; Python stages write at disengage and the Rust stage finalizes when the core disarms. |
| `position_multiplier` | `1.0` | Scale on hand **position** (not orientation): the EE target moves this many times as far as the hand. `>1` extends reach when the arm is longer than the operator's |
| `rotation_multiplier` | `1.0` | Scale on hand **orientation** (not position): the EE target rotates this many times as far as the hand. `>1` rotates the arm further than the wrist |
| `reset_speed` | `0.1 rev/s` | Average joint velocity of the worst-case joint during return-to-rest (peak is `1.5×` this) |
| `reset_min_duration` | `1.5` s | Floor on return-to-rest duration so near-rest starts don't snap home |
| `rest_pose_left` / `rest_pose_right` | near-zero | Reset target for each arm, shape `(7,)` in `ARM_JOINTS` order |
| `reengage` | `"ramp"` | What a grip does when an arm [re-engages](/guides/vr-interface#re-engaging) after a freeze / pause. `"clutch"`: the arm stays put and the controller's current pose becomes its origin (you match the arm). `"ramp"`: the arm eases out to where the controller is under the mapping from its previous engage (the arm matches you), then tracks 1:1. Switched live from the headset's **Ramp** button or the control panel's session settings via `VRTeleopCore.set_reengage()` (a [live setting](/api/vr#live-session-settings)); a reset drops the anchor, and box mode ignores it |
| `reengage_ramp_speed` | `0.15` m/s | Pace of the `"ramp"` blend: a 30 cm gap takes at least 2 s |
| `reengage_ramp_min_s` | `0.75` s | Floor on the `"ramp"` blend so a small correction is eased, not stepped |
| `box_mode` | `False` | Start in [box mode](/guides/vr-interface#box-mode): grippers held as a level parallel pair clamping the box between their sides (the fitted tool's flat contact face against each side) and one grip driving both arms by **position and heading** — the pair follows the hand's translation and its turn about vertical (about the pair's centre) and stays level whatever the hand's pitch and roll (the other grip hands over the lead). Switched live from the headset's **Box** button, both thumbstick clicks together, or the control panel via `VRTeleopCore.set_box_mode()` (a [live setting](/api/vr#live-session-settings)); the sticks set the grip width and tilt while a grip leads it and drive Jelly once it's frozen. A switch engages at once: into box mode led by `box_lead_hand`, out of it with both arms (in ramp re-engage both blend back out to the session's controller↔arm mapping, which box mode leaves untouched), unless the first frame comes more than a second later (switched with nobody in the headset) — a return to rest that leaves box mode never engages |
| `box_lead_hand` | `"right"` | Which controller leads the pair when box mode is switched on (`"left"` / `"right"`); the other grip can still take the lead over. Live setting |
| `box_grasp` | `"straight"` | Which of the two grasps a session starts in: `"straight"` — fingers straight forward (0°), width between the mounts, the blade opening to its stop like everywhere else; `"flush"` — the fitted tool's contact face along the box side (parcel gripper: the blade held at `box_tool_open_deg` instead of its stop — `VRTeleopCore.gripper_open_limit` → `AxolArm.set_gripper_open_limit` — `180° − box_tool_open_deg` inward yaw, width between the faces). Toggled live by clicking (and releasing) either thumbstick while a grip leads, or as a live setting; a live pair blends into the new grasp over `box_align_duration`. The worker reports the current grasp as `pair.grasp` and the core mirrors a stick toggle back into this field |
| `box_tool` | `"parcel"` | Which gripper is fitted, for box mode's contact geometry (`almond_axol.teleop.box.ToolGeometry`). `"parcel"`: the hinged-blade [parcel gripper](/guides/vr-interface#box-tool) — in the `"flush"` grasp each gripper is yawed `180° − box_tool_open_deg` inward so the folded blade's flat face lies parallel to the box side, and `width` is the distance between the two faces. `"urdf"`: the stock two-finger gripper — mounts `width` apart, fingers straight forward at tilt 0. Live setting; read at each engage |
| `box_tool_open_deg` | `140` ° | Parcel gripper: the hinged blade's angle in the angled (`"flush"`) grasp, degrees of motor rotation from closed. There the gripper is held at this opening rather than its stop (the trigger's travel spread over it) and yawed `180°` minus this inward (40°) so the folded face lies along the box side; everywhere else the blade opens to its stop, whose angle is never assumed. If the face only sits flat at a nonzero tilt trim, subtract the trim here. Live setting |
| `box_face_left` / `box_face_right` | `"auto"` | Which flat side of each gripper (mount `"+x"` / `"-x"`) is turned toward the box. `"auto"` picks the one needing the smaller wrist turn at the engage — pin it for the parcel gripper if it engages with the fixed blade toward the box or the motor cap down. Live settings |
| `box_grip_tilt` | `0` ° | Fixed inward yaw *trim* of each gripper on top of the grasp's yaw: `0` holds the contact face parallel to the box side; positive turns the fingertips toward the box centre, negative splays them outward, pivoting about the contact face. A calibration constant (e.g. a few degrees negative to land the parcel gripper's proud tip on the face plane), not a live control
| `box_width_speed` | `0.08` m/s | Rate either stick's left/right changes the grip width — the lateral distance between the two contact faces (the mounts, for the URDF gripper) — push right = wider. Only a stick's dominant axis counts, so width and tilt never change together |
| `box_width_min` / `box_width_max` | `0.02` / `0.70` m | Clamp on that width. The floor is raised, per grasp, to where the fitted tool's bodies would meet a centimetre apart (`ToolGeometry.min_width`): the parcel gripper's flush faces are proud of the wrists and close to `box_width_min`; the straight grasp (face on the mount axis) stops at ~`0.077` |
| `box_align_duration` | `1.5` s | Smoothstep blend from the arms' actual poses into the parallel pair when engaging in box mode |
| `box_elbow_out` | `30` ° | How far out box mode holds the elbows: degrees from straight down, toward the arm's side, that an IK elbow hint steers each elbow's free swivel to (`0` under the arm, `90` level). Either thumbstick's forward/back jogs it live (forward = further apart) and the worker reports the value back through `pair_status` (`"elbow"`), which the core mirrors into the config — so it outlasts the pair and shows in the panel |
| `box_elbow_weight` | `10` | IK weight on that hint (gripper `pos_weight` is 50). `0` disables it — the elbow swivel is then left alone, kept off the base by the arm↔torso collision model (`KinematicsConfig.self_collision`) — and the sticks' elbow control does nothing. Off by default: a second cost pulling on each arm during a move, kept out until the pair's alignment is settled without it |
| `box_elbow_speed` | `30` °/s | Rate the sticks change `box_elbow_out` at full forward/back deflection |
| `box_squeeze_torque` | `0` Nm (off) | Box mode's opt-in hard per-joint squeeze cap: while box mode is on (and no return-to-rest is playing) the impedance spring torque of `shoulder_2` and `shoulder_3` on each arm — the joints a lateral force at the gripper loads, and not the ones that lift the box — is capped here. `VRTeleopCore.spring_caps()` reports the caps in force; the adapter hands them to the robot (`set_spring_caps`), which backs each whole-arm command off toward the measured pose until the capped joints are within their caps and also sends them with each command for the realtime core's per-joint clamp. A backstop under `box_squeeze_force` — but a per-joint torque cap cannot tell a squeeze from a move (the shoulders' servo lag during a carry exceeds any useful cap), so with it on the arm moving toward the other trails and the pair skews; off by default. Live setting; realtime-core hardware only |
| `box_squeeze_lean` | `1` (×) | Box mode's squeeze lean, scaled (`0` = off). A plain lateral run-ahead into the box is a force at the gripper mount plus the moment it takes to hold the mount's orientation against the arm's stiffness coupling, which the tool's contacts can only carry by loading unevenly (the face digs in, the tip lifts). From each arm's Jacobian at its commanded pose (`GravityCompensator.mount_jacobian`) and its joint stiffness (`AxolArm.kp`), `almond_axol.teleop.box.squeeze_lean` gives the target offset — an inward yaw of ~1.3° per cm of clamp depth, a touch of roll, a millimetre of translation — that makes the run-ahead a pure force through the contacts' centroid (`ToolGeometry.contacts`: the parcel blade's root corners and its tip), which they share evenly. The IK worker adds it to each gripper target in proportion to the measured clamp depth: the raw targets' run-ahead past the measured mounts along the pair's inward normals, averaged over both arms (a carry adds nothing) and low-passed 0.2 s. The core forwards the arms' measured joints and `kp` before every box-mode frame (`VRTeleopCore.run_ik_loop(get_measured=measured_arms)` → `IKWorker.note_measured`). Target-side only: nothing on the command path changes, and no arm is held back. `pair_status["squeeze"]` reports the force. Live setting; realtime-core hardware only |
| `box_squeeze_trim` | `5` (°) | Bound on box mode's squeeze trim (`0` = off). The lean is open loop and the arm is not quite its model (gear backlash, wrist give, the gripper flexing under load), so a heavy box — more depth for the friction to carry it — still pinched. The worker measures the toe-out the encoders do see — the yaw between each gripper's measured mount rotation and its parallel slot (`almond_axol.teleop.box.toe_out`), signed tip-out and averaged over the two arms so a turn's servo lag cancels — and while the grippers press integrates it (1°/s per degree) into an extra inward yaw of both targets, never more than this, bleeding off over a second once they don't. `pair_status["trim"]` reports it in degrees. Live setting; realtime-core hardware only |
| `box_squeeze_force` | `0` N (off) | Cap on box mode's clamp force per arm. The lean knows the force the depth produces (~6 N per cm); past the cap the worker pulls the targets back out along the normals to the cap's depth, by the same amount on both arms, so the pair presses with the cap however far the width is jogged, at any pose. Live setting; realtime-core hardware only |
| `absolute_mode` | `False` | Mantis mapping: fit one gravity-aligned world→robot-base transform at the deliberate two-control engage gesture, then map live poses 1:1 in that fixed frame |
| `base_height` | `None` | Optional robot-base height in the pose producer's world; `None` derives it from the two held start poses |
| `tcp_transform_left` / `tcp_transform_right` | `None` | Tracker→gripper TCP transform `[x, y, z, qx, qy, qz, qw]`. Explicit and file-loaded values must contain seven finite numbers, a translation no farther than 1 metre (values are metres, not millimetres), and a nonzero quaternion. Explicit values are useful for bring-up captures; production Mantis collection also requires each final value to match the active device/profile-keyed entry in `~/.almond/mantis/tcp_transform.json` (or a verified factory constant), so a stale value cannot survive a tracker-source swap |
| `tracker_key` | `None` | Quest's exact `quest:<WebXR-profile>:grip` transform identity. Lighthouse and Ultimate ignore this singular field and resolve their distinct left/right `survive:<id>` / `ultimate:<mac>` bindings from tracker config. Saved Ultimate entries also carry the quaternion-order/up-axis pose convention and become non-authoritative if it changes |
| `quest_controller_profile` / `quest_pose_space` | `None` | Expected live Quest controller datum, normally derived from `tracker_key`; a mismatch makes that side untracked and forces recovery instead of applying the wrong mount transform |
| `urdf_viewer_world_aligned` | `None` | Spatial-overlay policy. Mantis setup resolves `None` to true for Quest and false for Lighthouse/Ultimate, whose world is unrelated to a view-only Quest. Set true for an external source only after an out-of-band origin/yaw co-registration |

<Note>
  **Engage behaviour.** From rest, both grip buttons together engage both arms. Once engaged, each grip acts **per arm** — a click toggles that arm between tracking and frozen (a frozen arm holds its pose and grasp while the other keeps tracking). Set `hold_to_engage` for a dead-man scheme instead: hold both grips to start, release one to freeze that arm, hold on to keep it going. A rising edge on the reset button triggers a trajectory back to the rest pose (collision-aware when `KinematicsConfig.self_collision` is on; joint-space with limits otherwise). In **box mode** the pair engages on the switch itself, led by `box_lead_hand`; from a frozen pair a single grip engages both arms again, blending them into the parallel pair first, and the pressed controller leads.

  **Re-engaging.** When a grip re-engages an arm (after a freeze, a disengage, or the arm being moved by hand), `reengage` decides who moves: with `"clutch"` nothing does — the controller's current pose becomes the new origin — while with `"ramp"` the IK worker keeps the controller↔arm mapping from the arm's previous engage and blends the arm's target from its current pose to where that mapping places the controller (smoothstep, paced by `reengage_ramp_speed` with a `reengage_ramp_min_s` floor; the goal is live, so a moving hand is followed). The engage-edge frame itself never moves the arm in either mode. The mapping is dropped by `IKWorker.reset()` / `clear_engage()` (return to rest, DAgger sync), so the first engage after those snaps fresh regardless of mode.

  **Live settings.** `box_mode`, `reengage`, `hold_to_engage`, `position_multiplier` and `teleop_max_vel` (plus the grippers' torque limit on hardware) can change while a session runs — from the headset HUD or the control panel — through `almond_axol.teleop.live.LiveSettings`, which validates a request and hands it to `VRTeleopCore.set_live(key, value)`. Requests are queued and applied on the IK thread before the next frame (or while idle), and fields the IK worker reads are mirrored to it as `("set", key, value)` messages, so the two processes' copies of the config never disagree mid-step. See the [VR server API](/api/vr#live-session-settings) for the wire protocol.
</Note>
