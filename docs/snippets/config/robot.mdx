<Accordion title="Tracking experiments (opt-in)">
  Candidates for stiffening the arm and removing its slow-motion stick-slip stairs, each behind a flag so they can be A/B'd on hardware one at a time. With every flag at its default the controller is exactly the production one. They run in the realtime core (which logs a warning naming the active set), and the control trace gains `stiction_ff` / `integral_ff` columns to read them by. Measure with [`tune.motion`](/cli/tune-motion) — `--experiment name=value` per run, or an `experiments` block in the settings file, with the resolved set printed at startup and saved on the run — plus an `AXOL_RT_TRACE` capture, and check the 3 / 8–13 / 27–35 Hz modes stay quiet. Requires a core rebuilt from the same checkout (`axol rt.install`).

<Warning>
  These do **not** apply under [`tune.pid`](/cli/tune-pid). Its single-joint runner is a separate control law living in the core's tuning path, with none of this plumbed into it, so every flag here reads as a no-op there. Only the production `motion_control` path — teleop, `tune.motion`, `tune.repeatability` — runs them.
</Warning>

  | Flag | Default | Description |
  |---|---|---|
  | <F>--{prefix}experiments.friction_k_max</F> | `100.0` | Steepness cap on the Coulomb friction feed-forward. At the default the feed-forward delivers only ~20 % of `fc` at 0.02 rad/s (~46 % at 0.05), which is what makes slow extended-reach moves creep in stairs; at 400 those become ~66 % / ~96 %. Pair with `friction_slew`. |
  | <F>--{prefix}experiments.friction_slew</F> | `0.0` | Rate limit (Nm/s) on the Coulomb term, `0` off. Keeps the ±`fc` reversal step off the shoulders' 2–3 Hz mode once the cap is raised; try 20–40. |
  | <F>--{prefix}experiments.friction_load_gain</F> | `0.0` | Load-dependent friction: `fc + gain × |gravity torque|`. Gear friction rises with load and the fits were taken at moderate poses; try 0.03–0.1. |
  | <F>--{prefix}experiments.stiction_gain</F> | `0.0` | Error-sign Coulomb compensation as a fraction of `fc`, pushing toward the target while the joint is stuck and the velocity feed-forward is off. `0` off, 0.6 suggested; keep under 1 (hunting), and prefer a robot with its own [`tune.friction`](/cli/tune-friction) fit. |
  | <F>--{prefix}experiments.stiction_err_deg</F> | `0.1` | Position error (degrees) at which that term saturates. |
  | <F>--{prefix}experiments.integrator_hz</F> | `0.0` | Crossover (Hz) of a slow, clamped position-error integrator on the feed-forward torque; `0` off, 0.3 suggested. Closes the static error the PD loop parks with; if the stairs grow it is too fast. |

  | <F>--{prefix}experiments.integrator_clamp_min_nm</F> | `0.3` | Floor (Nm) on that bound, for the low-friction wrists. |
  | <F>--{prefix}experiments.integrator_freeze_deg</F> | `2.0` | Position error (degrees) above which the integrator holds instead of winding up. |
  | <F>--{prefix}experiments.tracker_wire_vel</F> | `false` | Send the core tracker's own velocity as the wire velocity instead of a lagged derivative, so firmware `kd` stops braking during acceleration. |
  | <F>--{prefix}experiments.tracker_vel_pole</F> | `60.0` | Low-pass pole (rad/s) on that velocity. |
  | <F>--{prefix}experiments.tracker_accel_ff</F> | `false` | Drive the `j_eff` inertia feed-forward from the tracker's own acceleration instead of a double-lagged derivative. Re-fit `j_eff` with [`tune.pid`](/cli/tune-pid) when on. |
  | <F>--{prefix}experiments.tracker_accel_pole</F> | `60.0` | Low-pass pole (rad/s) on that acceleration; lower it if `inertia_ff` in the trace shows a 120 Hz comb. |
  | <F>--{prefix}experiments.dither_nm</F> | `0.0` | Peak amplitude (Nm) of a stiction-breaking torque dither on the feed-forward, `0` off. Keeps the joint's friction sliding instead of re-sticking between cycles — the third angle on the stairs, next to `stiction_gain` and `friction_k_max`. Start at 15–25 % of the joint's `fc`: enough to keep the contact moving, not enough to move the joint. |
  | <F>--{prefix}experiments.dither_hz</F> | `40.0` | Dither frequency. Has to clear the arm's structural modes (up to ~35 Hz) and stay under the Nyquist of the loop emitting it (120 Hz in the core), so roughly 40–80. |
  | <F>--{prefix}experiments.dither_square</F> | `false` | Square dither instead of a sine: full amplitude the whole cycle, so it breaks stiction at a lower peak, but its odd harmonics reach well above `dither_hz`. Try the sine first. |
  | <F>--{prefix}experiments.tracker_pos_gain</F> | `15.7` | Position-tracking gain (1/s) of the in-core target tracker — realtime core only. It is a first-order pole, so the shipped value is a **~55 ms lag**, and that lag is the largest tracking error on the robot: it reaches the end effector as path deviation proportional to commanded speed, measured as `1.4 mm + 58 ms × speed` (3 mm creeping, 36 mm at 0.6 m/s), which is what makes a curved path cut its corner. Raising it buys that back faster than proportionally, and spends it on the reason the tracker is slow — its velocity feed-forward peaks at the arm's structural resonance. Watch the 2–3 Hz band; ringing there is the ceiling. |
  | <F>--{prefix}experiments.command_lead_ms</F> | `0.0` | Phase lead (ms) on the **wire position only** — the frame carries `p_cmd + lead × v_tracker`. Realtime core only. Cancels the velocity-proportional tracking lag rather than reducing it, which works because both halves are known: the lag is measurable per joint (right shoulder_1 20 ms, right elbow 28 ms at `tracker_pos_gain` 62.8) and the velocity is the tracker's own acceleration-bounded state. The derivative chains, the stiction/integrator error and the trace's `cmd_p` all stay on the unled command, so error terms keep measuring real tracking error; the trace's new `wire_p` column shows what went out. One value covers every joint, so it is a compromise where the per-joint lags differ. Watch for overshoot at direction reversals — the lead is largest exactly where velocity is about to change sign. |
  | <F>--{prefix}experiments.tracker_vel_gain</F> | `62.8` | Velocity-tracking gain (1/s) of the same loop, `2·ωn` against the position gain's `ωn/2`. Keep the 4:1 ratio when changing `tracker_pos_gain` or the loop stops being critically damped. |
  | <F>--{prefix}experiments.dither_fade_vel</F> | `0.05` | Velocity (rad/s) the dither fades out over (~24 % left at this speed, ~4 % at twice it). It earns its keep at rest and through creep; above that it is heat and buzz. `0` never fades. |
</Accordion>

<Accordion title="Wire command mode (opt-in, realtime core)">
  Which CAN frame the **MyActuator** arm joints (`shoulder_1`…`wrist_1`) are commanded with. The Damiao wrists and the gripper are unaffected, and so is every passthrough tick (gravity comp, bring-up hold) and every limp tick — `kp = 0` with a gravity feed-forward is an impedance statement no position frame can carry, so those keep MIT whatever this is set to.

  The draw is command resolution: both position frames take the target as a 32-bit 0.01 °/LSB angle, 2.2× finer than the MIT frame's 16-bit `p_des`, and hand the position loop to firmware running far above the 240 Hz command rate.

  <Warning>
    The cost is telemetry. These frames answer on the 0x240 reply instead of the MIT feedback frame, so measured position comes back at **1 °/LSB** (45× coarser), velocity at 1 dps/LSB, and the torque channel is q-axis **current in amps**, not Nm — which the contact watchdog, `torque_residuals` and the trace's `meas_tau` all read as though it were torque. Host damping falls back to the motor's own reported speed. These are A/B modes for a tracking measurement, not a path to collect datasets on. The core logs all of this, plus each motor's stored position-loop acceleration, when it arms.
  </Warning>

  | Flag | Default | Description |
  |---|---|---|
  | <F>--{prefix}experiments.wire_mode</F> | `mit` | `mit`: the 0x400 impedance frame — the production control law. `a4`: 0xA4 absolute position closed-loop — a target and a speed cap, no torque byte, the firmware position loop doing the work. It is the command the tuning probes already use to park and hold the joints they are not testing, so that loop is known to carry these joints' gravity load, and there is no per-frame current cap to set too low. Like `a9` it sends no host feedforward. `a9`: 0xA9 force-control position closed-loop; the motor's position loop tracks the streamed trajectory under a torque and speed cap, and **no host feed-forward reaches the motor at all** — gravity, friction, damping, stiction, integrator and dither are inert, and the motor's stored position-loop PI is the whole controller, so a gravity-loaded joint holds only by winding up its own integral. `tf`: 0x73 position control with feed-forward torque — the same fine position command with the host feed-forward still arriving, quantised onto an int8. Needs V4.4 firmware; the core refuses to arm an older motor in `tf`. |
  | <F>--{prefix}experiments.wire_torque_pct</F> | `100.0` | `a9` torque limit, as a percentage of the motor's **rated current** (0–255, the wire unit — not Nm, not the MIT `t_max` scale). Above the motor's configured stall current the firmware leaves force control off entirely. |
  | <F>--{prefix}experiments.wire_speed_scale</F> | `1.0` | Multiplier on the joint's tracker velocity limit for the speed cap the frame carries. The trajectory is already inside that limit, so this is a runaway guard until you pull it below 1. |
  | <F>--{prefix}experiments.wire_ff_nm_per_pct</F> | `0.0` | Nm per 1 % unit of the `tf` frame's int8 feed-forward. `0` derives `t_max/100`, i.e. treats the MIT torque range as 100 % of rated — an assumption, not a measurement. Even at the default one step is ~0.6 Nm on an X6 against the MIT frame's ~0.03. |
  | <F>--{prefix}experiments.wire_torque_nm_per_amp</F> | `0.0` | Nm per amp of reported q-axis current, to put the reply's torque channel back into Nm. `0` reports raw amps. |

  Two commands from the same family are deliberately **not** offered. 0x72 (`SF`, position with feed-forward *speed*) scales its int8 against the motor's rated speed, which the motor does not report and this codebase does not know — and the MIT frame's 12-bit `v_des` does that job better anyway. 0xA1 (torque closed-loop) would move the whole impedance law onto the 240 Hz host loop, well below the firmware's inner rate.

  One thing these modes depend on is **not** settable from here: the motor's stored position-planning acceleration. At 0 the position loop tracks each target directly through its PI controller, which is what a streamed trajectory wants; at anything else the motor plans its own ramp to every one of the 240 targets a second it receives. The write command (0x43) stores to ROM and only accepts 100–60000 dps/s, so it cannot even express 0 — that is a deliberate change made once with the vendor setup software. The core reads the value at arm time and reports it per joint.
</Accordion>

</Note>
