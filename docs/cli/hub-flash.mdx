---
title: "hub.flash"
description: "Flash the bundled firmware onto the Axol and Mantis hubs."
---

Flashes the firmware image that ships with this package (`almond_axol/hub/axol_hub.uf2`) onto the Axol arm hub or the Mantis hub, which are the same board on the same firmware. The hub reboots into its RP2350 bootloader, the image is copied onto the bootloader's USB disk, and the command waits for the hub to come back as a CAN adapter and report the new version. Both of the hub's buses go quiet for a few seconds while it reboots. Flashing needs root: run as a normal user, the command finds the hubs and asks its questions first, then runs each flash through `sudo`, which asks for your password.

| Flag | Description |
|---|---|
| `--port PORT` | USB port path of the hub to flash (e.g. `1-3`, as printed by [`hub.info`](/cli/hub-info)). Also flashes a hub that is sitting in its bootloader, without asking. Default: every outdated hub on USB, plus any RP2350 bootloader you confirm at the prompt |
| `--force` | Flash even when the hub already runs the bundled version |

```bash
axol hub.flash
axol hub.flash --port 1-3
axol hub.flash --force
```

<Note>
  You normally never need this: every arm bring-up (teleop, data collection, policy runs and control-panel operations — whatever connects the arms through `Axol`) checks the hub's firmware version and reflashes an outdated hub automatically before any bus is opened. The hosted `axol serve` is root and flashes directly; a manual session asks for `sudo`. If it cannot escalate, the session keeps running on the old firmware and logs an error naming `axol hub.flash`. Set `AXOL_HUB_FLASH=0` to skip the automatic update. The Mantis hub is not updated automatically: run `axol hub.flash` with it plugged in.
</Note>

<Warning>
  A hub whose firmware predates 2026-08-17 cannot be rebooted into its bootloader from the host, so it needs **one manual flash**: unplug it, hold its BOOTSEL button while plugging it back in, then run `axol hub.flash`. After that, updates are automatic. The same manual flash recovers a hub that powers up (LED on) but never shows a CAN interface in `ip link show`. A hub left in its bootloader by an interrupted flash fails the bring-up; re-running `hub.flash` recovers it.

  A bootloader carries no identity of its own, so it could be any RP2350 board. `hub.flash` therefore asks before flashing one, and without a terminal it only prints the `--port` command. Pass `--port` to flash it without asking.
</Warning>

The hub's firmware decides what happens to motor commands when the bus dies. Since firmware 2.00, a USB reset ends the hub's CAN session and discards anything it had queued, and a frame that cannot be sent within 50 ms is dropped, so a command parked behind an emergency stop can no longer reach the motors when power returns. Firmware 2.01 also reports when nothing on a bus acknowledges frames, which is how the realtime core now detects a cut motor supply (see [`can.setup`](/cli/can-setup)).
