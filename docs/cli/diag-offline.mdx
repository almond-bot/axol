---
title: "diag.offline"
description: "Analyze a teleop recording offline to find whether jitter comes from wifi, filtering or IK."
---

Analyzes a teleop recording (`axol teleop --teleop.record PREFIX`) offline, with no hardware. Each suite checks one stage of the teleop pipeline, so you can tell where jitter comes from.

| Suite | Question | What it reports |
|---|---|---|
| `wifi` | Is the network connection jittery? | Time between VR frames (median, p95, p99, max), gaps over 100 ms, and bursts of frames. Gaps with steady IK timing point at the network, and with uneven IK timing at a busy computer. |
| `filtering` | What do the pose filters let through? | 3–15 Hz motion at each stage, from raw VR pose to the end-effector target, with the share passed through and the delay each stage adds. If a lot reaches the target, tune the filters, not the motors. |
| `kinematics` | Does IK add motion the hand didn't make? | Target versus achieved end-effector pose, solve time per tick, per-joint drift (°/min) without end-effector motion, and per-joint jitter with its main frequency. |

| Flag | Description |
|---|---|
| `suite` | `wifi`, `filtering` or `kinematics` (required) |
| `prefix` | Recording prefix used with `--teleop.record`, looked up in `~/.almond/recordings/` (default: the newest recording there) |
| `--save-run` | Save the analysis under `~/.almond/diagnostics/tuning/` for the diagnostics dashboard |
| `--label TEXT` | Note stored on the saved run |

```bash
axol teleop --teleop.record rec1         # record a session first
axol diag.offline wifi rec1
axol diag.offline filtering rec1 --save-run
axol diag.offline kinematics --save-run  # newest recording
```

The `kinematics` suite feeds the dashboard's **IK** tuning tab: target versus achieved pose charts, the solve-time trace and the per-joint drift scores.

See also [`diag.teleop-jitter`](/cli/diag-teleop-jitter), which breaks one recording down by stage and frequency band, and [`tune.motion`](/cli/tune-motion), which runs the tests on the robot.
