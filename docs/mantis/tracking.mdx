title: "Mantis Tracking"
description: "Set up Meta Quest, VIVE Tracker 3.0 (Lighthouse), or VIVE Ultimate tracking as the Mantis pose source."
---

Mantis **data collection** needs a **pose source**: the tracking system that reports where each rig is. (Mantis teleop never tracks; it drives the grippers straight from the rig triggers.) Mantis supports three sources, selected under **Mantis settings → Tracking** in the control panel (default: Lighthouse). Pick one per installation: the choice, its setup state, and its device bindings are all stored on the host, so every collection run uses the same source without per-run flags.

| Source | Hardware | Tracking | Setup contract |
|---|---|---|---|
| **Quest** | Meta Quest controllers via WebXR | Headset inside-out tracking | Enter VR in the headset browser; handedness identifies left/right. No bridge, no Identify. |
| **Lighthouse** | VIVE Tracker 3.0 | Outside-in, configured SteamVR base stations | Pinned libsurvive runtime, paired trackers, station survey, identified sides, current guided validation. |
| **Ultimate** | VIVE Ultimate Tracker | Inside-out SLAM, no base stations | One-time pair + room map in VIVE Hub on Windows; then the HTC dongle and pinned pyvut runtime on the host, private shared-map AP config, identify sides. |

<Note>
  Keep the product names distinct: **VIVE Tracker 3.0** is the Lighthouse device (there is no "Quest 3.0" tracker), **Meta Quest** is the WebXR source, and **VIVE Ultimate Tracker** is the inside-out source.
</Note>

Before starting, finish the [Mantis hardware setup](/mantis/hardware): the hub connected, **Mantis** selected on its tile, the CAN side mapping confirmed, and the grippers-only teleop check passed. Then open **Mantis settings → Tracking** and choose the source; the selection saves to the host immediately, so runs and the setup actions below always use it.

## Set up the source

The Tracking tab walks each source through a **step-by-step flow**. Each step resolves from what the host actually reports (not from ticking a box), **Continue** unlocks once it is resolved, a step that regresses later pulls the flow back to it, and the flow stays on a step while its action is running. The device setup flow ends once the sides are identified (or, for Quest, once the headset's calibration key is saved). Lighthouse collection also requires a current pass from the always-visible **Lighthouse tracking quality** card. The equivalent CLI commands are listed alongside; see the [tracker CLI reference](/cli/tracker) for their flags.

<Tabs>
  <Tab title="Quest">
    Quest uses the headset's own controller tracking through WebXR, so there is no runtime to install and no tracker to bind; WebXR handedness assigns left and right. The only stored state is the **calibration key** that identifies the controller generation and pose datum.
    <Steps>
      <Step title="Source">
        Choose **Quest** (the selection saves immediately). The Quest headset and the host must be on the same LAN (or use the wired [Quest-over-USB](/guides/quest-over-usb) link, managed under **General settings → Quest**).
      </Step>
      <Step title="Headset">
        Start a Quest **bring-up collection run**: `axol collect-data --mantis true --mantis_allow_uncalibrated true` (or Start **Collect data** with `mantis_allow_uncalibrated` set under Advanced); teleop never starts the VR server. Then in the Quest browser open [axol.almond.bot](https://axol.almond.bot), enter the host, connect, accept the host's certificate the first time, and choose **Enter VR**. Hold both Touch controllers.

        The step shows each controller's reported WebXR profile and pose space and, when both match, a copyable **common calibration key** (for example `quest:oculus-touch-v3:grip`). Press **Use this key**, then **Save settings**. The step resolves once the saved key is a **grip-space** datum matching the live controllers; a stale report, a `target-ray` fallback, or two controllers reporting different keys is held rather than accepted.
      </Step>
    </Steps>

    The client sends `gripSpace` poses (with `targetRaySpace` only as an older-runtime fallback), works without body/elbow tracking, and preserves lost optical tracking per side so the server can hold safely. Quest 3 Touch Plus controllers in the standard cradle use a **built-in factory tracker→gripper transform**; other controllers need a bench-measured transform for both sides under the exact saved key. See [Transforms](#transforms).
  </Tab>

  <Tab title="Lighthouse">
    Lighthouse tracks two **VIVE Tracker 3.0** units with the pinned [libsurvive](https://github.com/collabora/libsurvive) runtime on the host. Mount compatible base stations rigidly with the whole Mantis workspace in view. Give each **Base Station 2.0** a different channel. In **Lighthouse tracking quality**, select the number actually installed (1–4); choose **3** for a three-station setup. A survey that sees only two must not certify that installation.
    <Steps>
      <Step title="Source">
        Choose **Lighthouse** (the selection saves immediately).
      </Step>
      <Step title="Runtime">
        `axol provision` normally installs the pinned libsurvive build during installation. If the step is red, press **Install Lighthouse support** (CLI: [`axol tracker.install`](/cli/tracker#axol-trackerinstall)). It builds `survive-cli` at the pinned commit with Axol's native fixes, Eigen and the native libusb backend, and installs the Vive udev rule. It is safe to rerun: a build matching both the upstream revision and Axol patch revision is re-attested; an older build is rebuilt.

        When upgrading to fixed-geometry tracking, stop collection, run the installer, then restart `axol serve` so the hosted collector uses the updated code. Complete **Recalibrate Lighthouse** afterward. Existing validation reports from the previous refining mode do not qualify the updated collection mode.
      </Step>
      <Step title="Trackers">
        Power the base stations. For each tracker, unplug it from USB so it blinks blue, plug its Watchman dongle into the host, and press **Pair tracker** (CLI: `axol tracker.pair`). Then, with both trackers powered and in view, press **Check base stations** (CLI: [`axol tracker.lighthouse.check`](/cli/tracker#axol-trackerlighthousecheck)): it listens for about 20 seconds, extending to 150 seconds when live stations are seen but poses are still pending, and checks channels and reporting devices. This survey checks reception, not pose quality; complete the guided validation below before collecting.
      </Step>
      <Step title="Identify sides">
        Press **Identify trackers** (CLI: [`axol tracker.identify --backend survive`](/cli/tracker#axol-trackeridentify)). Identify watches which tracker moves for each side: move **only the requested rig** during each 3-second capture. It saves each side's physical serial; runtime codenames are not stable device identities. Re-identify older codename-only bindings before collection.
      </Step>
      <Step title="Validate tracking">
        In the always-visible **Lighthouse tracking quality** card, select the expected station count and press **Validate tracking**. Start with both rigs **still on the table**, with their trackers visible to the stations. No fixed reference fixture or precisely measured separation is needed. Follow each prompt: a **5-second stationary hold**, a **12-second slow workspace sweep** including at least **10 cm of travel and 15° of wrist rotation per rig**, then a **5-second stationary hold at another working position**. Move during the sweep and leave the rigs untouched during each hold. The result reports reception and tracking consistency; it does not certify absolute accuracy.

        Initial station acquisition can take **up to two minutes** before those measurements begin. The log shows received channels, decoded identities, and any identities still pending. Tracking can be ready before a complete identity broadcast arrives. Keep both trackers visible and wait for the next prompt; restarting the check starts acquisition over.

        Validate before the first session each day. Reports expire after **12 hours**; missing, failed, expired, or invalidated reports block collection. Fix the reported visibility, identity, or station issue and repeat the check. If a station or tripod moved or the calibration is suspect, press **Recalibrate Lighthouse**. First follow the preparation prompts: rest both rigs at **three different workspace positions and orientations for eight seconds each**, keeping their sensors visible. These pauses provide stationary views to the calibration solver. The command then stops that process and starts a fresh tracker against the saved candidate, with station geometry fixed as it will be during collection. Complete the scored hold–sweep–hold checks in this second process. A candidate calibration replaces the previous one only after it passes; a failed candidate leaves the previous calibration intact. A failed phase stops the procedure and displays grouped failure summaries. Stop any active operation before either command.

        With both sides already identified, a successful **Recalibrate Lighthouse** includes validation. When it shows **Tracking check passed**, there is no need to press **Validate tracking** immediately afterward. A station-identity acquisition error alone does not mean the tripods moved or that calibration must be repeated; the check must receive each station's identity as well as its tracking sweeps.

        If **Identify sides** fails because tracking is unstable, use **Recalibrate Lighthouse** first. Recovery can detect two trackers without assigning left/right. When it reports **Calibration saved — identify sides, then validate tracking**, complete those two steps before recording. A green tracker LED indicates normal device mode; a station check with only one fresh pose can still reflect a tracking or calibration failure rather than lost pairing.
      </Step>
    </Steps>

    Lighthouse world calibration and the tracker-to-gripper mounting transform are separate. Recalibration updates the station world; it does not change the standard flat-back mount's built-in factory transform or repair already recorded poses.
  </Tab>

  <Tab title="Ultimate">
    **VIVE Ultimate Trackers** track themselves (inside-out SLAM) against a room map they share over a private access point, with no base stations or headset. There is no official Linux support; the host uses the community [pyvut](https://github.com/nijkah/pyvut) driver to talk to the **wireless dongle over USB HID**. Pairing and mapping are Windows-only, one-time operator steps; everything after that runs from the control panel.
    <Steps>
      <Step title="One time on Windows: pair">
        On a Windows PC install SteamVR, enable its [null/virtual-headset driver](https://github.com/username223/SteamVRNoHeadset), install VIVE Streaming Hub, and install the **VIVE Ultimate Tracker service** inside VIVE Hub ([pinned pyvut setup](https://github.com/nijkah/pyvut/blob/fcfcd33f4c1f16b0d84f5f741dc1319abdc7942a/README.md#constructing-map-steamvr--vive---only-available-on-windows), [HTC pairing prerequisites](https://business.vive.com/us/support/ultimate-tracker/category_howto/pairing-ultimate-tracker-with-the-dongle.html)). Connect the wireless dongle and open **Settings → VIVE Ultimate Tracker → Trackers → Pair new**. Power on a tracker, wait through its green/blue startup flashes until the LED is solid blue, then hold Power for about two seconds until blue flashes again and pair it. Repeat for the second tracker on the same dongle.
      </Step>
      <Step title="One time on Windows: map">
        Choose **Start setup → Create map**, establish the center, and scan the entire Mantis operating volume from both low/kneeling and standing heights while facing all four directions. Let the map auto-save (use Refine/Save if offered) and confirm both trackers regain full position + rotation after a power cycle. The pairing and map live on the trackers and move with them to the robot host.
      </Step>
      <Step title="Source">
        Back in the control panel, choose **Ultimate** (the selection saves immediately).
      </Step>
      <Step title="Runtime">
        Press **Install / Repair Ultimate support** (CLI: [`axol tracker.ultimate.install`](/cli/tracker#axol-trackerultimateinstall)). It installs the pinned pyvut commit, the `hid` Python binding, system HID libraries, and a persistent udev rule for dongle `0bb4:0350`; safe to rerun. Do not replace it with an unpinned `pip install` or a one-off `chmod /dev/hidraw*`.
      </Step>
      <Step title="Dongle">
        Plug the same dongle into the host. The step resolves when the dongle is detected, its HID endpoint is accessible, and the operator has USB access. The one host-side step, adding the Axol login to the `dialout` group, is shown with its command because it needs a re-login.
      </Step>
      <Step title="Wi-Fi">
        Save the trackers' **private shared-map AP** configuration: SSID, password, two-letter regulatory country, and Wi-Fi center frequency in MHz. These are **not** the Windows PC's network, the robot LAN, or your router. Upstream pyvut requires all four as fallback; with the USB-dongle transport the tracker firmware reports the active SLAM-host SSID/password/frequency and only the saved country is consumed directly. The password is masked and never read back, and the file is written as `~/.almond/tracker/ultimate_wifi.json` with mode `0600` (CLI/manual shape in the [reference](/cli/tracker#ultimate-wi-fi-file)).
      </Step>
      <Step title="Identify sides">
        Power both trackers inside the mapped area and press **Identify trackers** (CLI: [`axol tracker.identify --backend ultimate`](/cli/tracker#axol-trackeridentify)). Move only the requested rig for each side; the addresses are saved separately from Lighthouse bindings. Setup is complete once both sides are bound. [`axol tracker.ultimate.check`](/cli/tracker#axol-trackerultimatecheck) is an optional non-invasive host check that reports the same dependency, USB, permission, binding, convention, and redacted AP-config state the Start gate uses.
      </Step>
    </Steps>

    <Warning>
      The dongle protocol is reverse-engineered and firmware-dependent. The pinned runtime and factory transform expect `wxyz` quaternions and a z-up SLAM world. Bench-check gravity, translations, and rotations before changing those settings, and never use the quaternion/up-axis toggle to compensate for a mount transform: a convention change disables the factory transform and makes saved Ultimate overrides stale, blocking production use until an override is saved under the active convention or the pinned convention is restored.
    </Warning>

    The standard flat-back mount uses the **built-in factory transform** (the Tracker 3.0 value with the 11 mm origin difference folded in); nothing needs measuring.
  </Tab>
</Tabs>

The readiness the flow shows is also enforced by the operation backend: a direct CLI or REST start cannot bypass the runtime, permission, dongle/AP, binding, live-input, or production-transform gates.

## Start gesture and recovery

<Tabs>
  <Tab title="Quest">
    Hold both rigs at the agreed start pose, **release both controller grips, then press both grips together** to align and engage. The controller triggers operate the grippers. In data collection, **A** starts and confirms a take, exactly as on Axol.

    If tracking is lost on either side, both sides freeze. Restore both, then release and press both grips again; recovery never resumes motion on its own. **Reset** returns to rest and needs the same fresh gesture.
  </Tab>
  <Tab title="Lighthouse / Ultimate">
    A managed run does **not** move as soon as the trackers appear. Startup waits for **both fresh, fully tracked poses and both trigger heartbeats**. Then hold both rigs where the session should begin, **squeeze both rig triggers together, and release both**: on that release the world→robot base transform is fitted at the rigs' pose and tracking engages. In data collection the same gesture also starts the take (once the teleop core acknowledges the engage); while recording, rapidly fully squeeze and release either trigger **three times** to save or **four times** to discard.

    A tracker-lock loss or stale trigger heartbeat freezes both sides. Restore both, then repeat the both-squeeze→release gesture; nothing re-anchors automatically. **Reset** returns to rest and requires the gesture again.

    A Quest may still connect as a **view-only** passthrough / video / HUD client: its controller frames are ignored and never blend with the managed tracker bridge. Because there is no built-in Quest↔tracker world-registration procedure, the spatial URDF overlay is hidden for these sources by default.
  </Tab>
</Tabs>

## Transforms

Absolute (Mantis) IK solves the world yaw and translation at engage time, but it does **not** discover where the gripper TCP sits relative to the tracker. That rigid **tracker → TCP transform** must come from somewhere:

| Source | Transform |
|---|---|
| Lighthouse (Tracker 3.0) | Built-in factory value `[0, 0.035, 0.047, 0, 1, 0, 0]` (`Ry(180°)` flat-back mount rotation; tracker 47 mm behind and 35 mm above the gripper motor face) for both sides, applied automatically after Identify. |
| Ultimate | Built-in factory value `[0, 0.046, 0.047, 0, 1, 0, 0]` for both sides (Tracker 3.0's mount rotation with the 11 mm origin rise), approved for the pinned `wxyz` / z-up convention. |
| Quest 3 (Touch Plus) | Built-in factory values for `quest:meta-quest-touch-plus:grip`, mirrored between the left and right cradles (grip origin 62 mm behind and 45 mm above the gripper motor face), selected automatically when no Quest entry is saved. |
| Other Quest controllers | No factory value: measure the gripper TCP in each controller's grip frame and save it under the exact `quest:<reported-profile>:grip` key for both sides. |

<Warning>
Mantis datasets recorded with axol ≤ 0.2.4 used an `Rx(+90°)` Vive rotation that pitched every recorded gripper ~90° away from the operator's hold; Axol could not replay them. Repair them with [`axol migrate-dataset --mantis-tcp-rotation`](/cli/migrate-dataset#mantis-tracker-gripper-rotation) before replay or training.

axol 0.2.5–0.2.16 shipped a Vive translation (`[0, 0.0355, -0.092]` / `[0, 0.0465, -0.092]`) that put the tracker 92 mm in front of the gripper instead of 47 mm behind it. `collect-data` refuses to append to a dataset recorded with it; record to a new `repo_id`.
</Warning>

Overrides and Quest measurements live in `~/.almond/mantis/tcp_transform.json`, keyed per side by the identified device (`survive:<tracker serial>`, `ultimate:<mac>`, or `quest:<profile>:grip`). `pos` is the gripper TCP origin in the tracker's local frame in **metres**; `quat` is the TCP orientation in that frame as **`[qx, qy, qz, qw]`**. The file is edited directly (or via `PUT /api/tracker/calibration/<source>`); the panel does not edit transforms. The full schema, the Ultimate convention rules, and the bring-up route for a missing constant (`--mantis_allow_uncalibrated true` for a calibration-only capture) are in the [tracker CLI reference](/cli/tracker#transform-file). Production `collect-data` refuses to start with a missing, stale, or unapproved transform on either side.

## Acceptance

For Lighthouse, first pass **Validate tracking** with the guided hold–sweep–hold procedure. Validate before the first session each day; a report expires after 12 hours and is invalidated by changes to the tracked setup. A current pass is a preflight check; live tracking remains monitored throughout collection.

Before recording training data, run a short **bring-up collection run** (`axol collect-data --mantis true --mantis_allow_uncalibrated true`, discarding every take) with the workspace clear and check, with the selected live source:

1. Physical **left/right**, scale, every translation axis, wrist rotation, and tracker→TCP alignment. With Quest, the headset's live URDF overlay shows the virtual arms; with Lighthouse/Ultimate, use the control panel's mirrored view.
2. **Recovery**: deliberately occlude or de-localize one side and confirm both freeze; restore tracking and confirm nothing moves until the start gesture is repeated.

`tracker.identify` binds a tracker to a side by which one you move, not by which rig it is mounted on. If the tracker bound as *left* sits on the rig held in the right hand, the engage fit faces the robot base backwards and every recorded pose is yawed 180° with the columns swapped. With both sides calibrated, the engage refuses this: the log reports `Teleop engage rejected: both grippers face away from the robot's rest heading`, the session disengages, and nothing is recorded until both grips are released and squeezed again with the rigs in the correct hands (or re-identified). Hold each rig like the robot holds its rest gripper — fingers down, tracker face up, handle towards you — when engaging; a rig pointed straight up or down is not checked.

Recording also counts frames where a hand travelled beyond Axol's reach (`out_of_reach` in the episode QA line, plus a warning): the rig has no arm to stop you, but Axol cannot follow those poses on replay.

The episode controls show **Checking**, **Live tracking checks passed**, a warning, or a tracking fault. Recording waits for live tracking readiness. A reduced-redundancy warning may still permit recording; review its reason and restore coverage. A serious pose fault latches **Retake required**, disables **Save**, and remains attached to that take even if tracking subsequently recovers. **Discard and retake** stays available.

The final save check also checks recorded pose freshness and camera capture. A rejected take shows a separate red alert with the rejection reason. This stays visible when live tracking returns to green and the next take is ready; it clears when a new recording actually starts or an episode saves successfully. The saved counter advances only after a successful save. An intentional discard does not show a save error.

Mantis collection maps each incoming tracker pose directly through its mount calibration and the current engage transform, preserving the pose's capture timestamp. Recording does not wait for virtual-arm IK or use its causal pose filter. The virtual robot still runs IK, and the existing save-time zero-phase smoothing remains available. This avoids introducing virtual-arm processing delay into camera/pose alignment; stale or invalid tracker samples still fail the quality checks.

Recovery depends on the failure. For temporary visibility loss, restore coverage and wait for live checks to pass before starting a new take. For a persistent calibration fault, stop collection and run **Recalibrate Lighthouse**, which includes the required tracking validation; standalone validation is blocked until recalibration succeeds. For a stopped native tracking process, stop the session and investigate its process error; repeated recalibration does not repair a crashing runtime. Repair Lighthouse support if the runtime is outdated or damaged, retaining the session log if crashes recur. Smooth or fresh poses alone are not proof of spatial accuracy.

A source that jumps, drifts, swaps sides, or cannot recover cleanly is not ready for collection. Mantis teleop never tracks, and `axol teleop --sim --teleop.absolute_mode true` is only a generic mapping demo; physical acceptance must use the real source, Mantis selected, in a collection run.

## Automatic Lighthouse fault captures

Managed Lighthouse collection automatically arms a diagnostic recorder when live tracking first becomes ready. The episode panel shows **Automatic fault capture is ready**. Use the normal web UI and wireless trackers; no extra recording command is needed.

After a pose jump, stale pose stream, or left/right timing fault, the recorder saves up to **10 seconds before and 3 seconds after** the first fault. Keep the collection session open until the panel says **Tracking diagnostics saved**, then stop the session and retain the displayed directory. Captures are stored under `~/.almond/tracker/diagnostics/fault-*/`, containing `summary.json` and `events.jsonl.gz`. They remain available even when the faulty episode is discarded.

The trace includes native USB/HID callback times, IMU samples and device timecodes, solver suppression reasons, native poses with their original timecodes, optical observations, Python receipt times, and bridge timing/control state. Device clocks remain per-device; the summary distinguishes native monotonic time, estimated clock mapping, and Python receipt time. An input gap alone cannot distinguish wireless loss from a stalled native USB event loop.

Diagnostic writes use a separate nonblocking native pipe and background collector/writer threads. Each buffer is limited to 160,000 events and 64 MiB of encoded events; a session accepts at most three captures, separated by at least 30 seconds. Loss counters and truncated windows are explicit in the summary. These bounds can shorten the requested window under unusually high traffic. Diagnostic errors appear separately and do not change tracking acceptance or gripper control.

The current native build is `libusb-v4-tracking-quality`. It retains the Watchman timestamp-rollover fix and diagnostics, gives each tracker an independent CRC-checked base-station identity decoder, and enables per-measurement optical outlier rejection after tracking is established. Initial acquisition and calibration keep the filter disabled. These changes address software failure modes; they do not certify accuracy or eliminate physical occlusion and reflections. After updating the code, stop collection, run `.venv/bin/axol tracker.install` from the checkout, and restart `.venv/bin/axol serve`. Earlier native builds are rebuilt automatically. Build the web UI using the commands in `web/README.md` if it has not already been rebuilt. When upgrading from the previous refining mode, complete **Recalibrate Lighthouse** as described above. If the setup already uses fixed geometry, run **Validate tracking** to cover the updated solver; recalibrate when the setup has changed or the check requires it.
